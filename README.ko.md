# eg2-langid

[English](README.md) | **한국어**

EmbeddingGemma 2 오디오 임베딩 위에 얹은 **경량 언어 식별(language identification)** 패키지입니다.

768차원 오디오 임베딩 공간 위의 **175KB 선형 분류기** 하나로 **29개 언어**를 판정합니다.
LLM 호출 없이 CPU만으로 동작합니다. 임베딩 모델은 **패키지에 포함되어 있지 않으며**, 이미 구동 중인
EmbeddingGemma 2 ONNX 런타임에 붙어서 원본 오디오 또는 미리 계산된 벡터를 받아 동작합니다.

## 특징

- **29개 언어** (정답 라벨로 검증된 22개 + VoxLingua107에서 편입한 7개)
- **분류기 하나 175KB** — 필수 의존성은 `numpy` 뿐입니다 (음악/효과음 판정용 MIT silero VAD 2.2MB 동봉)
- **세 가지 통합 레벨**: 벡터 입력 · 오디오 + 임베더 콜백 · 선택적 모델 어댑터
- **미지 언어 게이트** — 알려진 언어 어디에도 맞지 않는 오디오를 거부합니다
- **라이브 데스크톱 위젯** — PC에서 재생 중인 소리의 언어를 5초 창으로 표시합니다
- **스트리밍 구조** — 임베딩은 계산 → 판정 → 폐기. 디스크에 아무것도 쓰지 않습니다

## 실측 성능

| 평가 | 결과 |
|---|---|
| 홀드아웃 gold (FLEURS test, 22언어 × 100건) | **0.9868** (2,171 / 2,200) |
| id/ms 쌍을 제외한 정확도 | **99.95%** (2,000건 중 1건 오답) |
| 5초 창 vs 전체 클립 | **98.2%** vs 97.7% |
| 3초 / 2초 / 1초 창 | 90.5% / 77.3% / 47.0% |
| 미지 언어 거부율 (오거부 5.5% 기준) | 37.5% |
| 임베딩 + 판정 지연 (5초 오디오) | 약 0.4초 (CPU 4스레드) |

남은 오답은 한 쌍에 집중됩니다 — 말레이어 ↔ 인도네시아어 (오답 29건 중 28건).
두 언어는 상호이해 가능성이 높아, 낭독체 음성만으로는 본질적으로 모호한 구간이 실재합니다.


## 사용법

### 1. 벡터 입력 (가장 가벼운 방식)

```python
from eg2_langid import LanguageIdentifier

li = LanguageIdentifier()
r = li.detect(vec_768d)
print(r)                 # "ko_kr (97%)"
print(r.lang, r.unknown, r.confidence)
```

### 2. 오디오 입력 + 직접 만든 임베더

```python
r = li.detect_audio(pcm_float32_16k, embed_fn=my_embedder, window_sec=5.0, hop_sec=1.0)
print(r.distribution)    # {'ko_kr': 0.8, 'en_us': 0.2}  — 창별 투표 비중
```

### 3. 내장 어댑터 사용 (모델 필요)

```python
from eg2_langid.adapters.gemma2 import make_embedder

embed = make_embedder()                                   # EG2_MMAL4_DIR 를 읽습니다
r = li.detect_audio(pcm_float32_16k, embed_fn=embed, window_sec=5.0)
```

### Result 필드

| 필드 | 의미 |
|---|---|
| `lang` / `label` | 승자 클래스(라벨은 {hi, ur} 그룹 표기 적용). 거부되면 `None` |
| `confidence` | **미지언어 게이트 임계 대비 여유** — `0`이면 간신히 통과, `1`이면 여유로움. 정확도 수치가 아닙니다 |
| `p_correct` | **이 판정이 맞을 확률**(gold margin 캘리브레이션). 위젯이 표시하는 값 |
| `margin` | 1위 점수 − 2위 점수 |
| `unknown` | 29개 언어 밖으로 판정되어 게이트가 거부 |
| `distribution` | 오디오가 한 창보다 길 때 창별 투표 비중 |

짧은 클립은 `confidence`가 0.02여도 정답일 수 있으므로, 화면에는 `p_correct`를 쓰세요.

### 음악 / 효과음 판정

5초 창을 **발화 포함 여부**로도 평가합니다. 말소리가 없으면 언어 대신 `kind='music'` 또는
`kind='sfx'`가 반환되고, 위젯은 (엉뚱한) 언어 대신 **음악** / **효과음**을 표시합니다.

```python
r = li.detect_audio(pcm, embed_fn=embed, vad_fn=vad)   # vad는 선택
r.kind          # 'speech' | 'music' | 'sfx'
r.p_nonspeech   # 0~1

# 선택: 언어 프로브 반응까지 사용 (11특징 → 17특징)
r = li.detect_audio(pcm, embed_fn=embed, vad_fn=vad, use_hybrid=True)
```

`use_hybrid=False`(기본)는 **파형만으로** 음악을 판정하므로 음악 창에서 ~0.4초 임베딩을 치르지
않습니다. `use_hybrid=True`는 프로브 반응(최고점수·margin·엔트로피·센트로이드 간격)을 더해
out-of-fold 기준 조금 더 좋지만(AUC 0.9851 → 0.9918, 기악 97.5 → 100%, 유튜브 오탐 4.3 → 3.6%),
모든 창에서 임베딩이 필요합니다. 데스크톱 위젯은 `EG2_HYBRID=1` 로 켭니다.

| 설정 | 발화 오탐 | 기악 | 보컬 음악 | 효과음 |
|---|---|---|---|---|
| **VAD 사용** (0.70) | **0.0%** | 97.5% | 75.0% | 93.6% |
| VAD 없음, numpy만 (0.85) | 0.0% | 71.6% | 68.3% | 53.2% |

파일 단위 교차검증 기준입니다 — 발화 129크롭(8개 언어 FLEURS), 기악 22곡, 보컬 20곡,
Windows 효과음 70개. `vad`는 `eg2_langid.adapters.silero_vad.make_vad()`로 만듭니다
(모델은 `eg2_langid/assets/silero_vad.onnx` 에 **동봉**되어 있습니다 — MIT © Silero Team.
`onnxruntime` 이 필요하고, 없으면 numpy 경로로 동작하지만 검출률이 낮아집니다).

**시끄러운 발화 편향 — 현장 지적으로 수정.** 클럽 인터뷰나 FPS 방송에서 음악으로 과다 판정되던 문제를
음수 SNR(음악이 말보다 큼) 믹스로 재현했습니다:

| 발화 + | 이전 모델 | 현재 모델 |
|---|---|---|
| 음악 0dB | 6.2% 음악 오판 | **0.0%** |
| 음악 −5dB | 18.8% | **0.0%** |
| 음악 −10dB | **37.5%** | **0.0%** |
| 게임 효과음 −10dB | 0.0% | 0.0% |
| 실제 유튜브 오디오 80창 | 3.8% | **2.5%** |
| 음악/효과음 검출률 | 95.0% | 81.7% |

두 가지를 바꿨습니다. 발화 클래스에 **믹스 240개**(발화+음악·발화+효과음, 0/−5dB, 곡 단위 분리)를
추가 학습했고, **VAD 가드레일**을 넣었습니다 — 창의 20% 이상이 발화로 잡히면 음악 판정을 취소합니다.
가드레일이 더 큰 효과를 냈고, 대가는 음악 검출률 하락(95%→82%)과 보컬 곡이 가사 언어로 표시되는
경우입니다.

**편향이 드러난 실제 영상 2개로 검증** (각 5분, 60창):

| | 클럽 인터뷰 (목소리 아래 음악) | 게임 방송 (효과음+음악) |
|---|---|---|
| 수정 전 | 창의 23.3%를 음악으로 | 48.3% |
| `verify_music` | **3.3%** | 45.0% |
| `EG2_HOLD=20` 적용 시 | **100% 시간 동안 언어 표시** | 90.0% |

클럽은 **VAD가 놓친 실제 발화**였습니다. 그 창들에서도 언어 프로브는 margin +0.59로 `en_us`를
보고 있었습니다(85%가 0.4 초과). 그래서 음악 판정이 나면 프로브로 한 번 재확인하도록 했고
(`verify_music`), `EG2_VERIFY`로 빈도를 제한해 음악만 재생될 때 임베딩 비용을 창당 0.4초가 아니라
약 7% CPU로 묶었습니다.

게임 방송은 다릅니다 — 남은 45% 구간에서 프로브도 언어 신호가 없습니다(margin +0.11, 0.4 초과 0%).
그 오디오는 실제로 효과음뿐입니다. 이 구간을 "한국어"로 읽히게 하는 것은 hold 타이머입니다
(12초 → 83%, 20초 → 90%, 30초 → 98%).

**실측 한계**
- 가창은 발화와 완전히 분리되지 않습니다 — 보컬 트랙의 75%만 음악으로 잡히고, 나머지는 언어로
  표시됩니다(가사가 실제로 그 언어이므로 틀린 판정은 아닙니다).
- 음악과 효과음은 약 20%가 서로 혼동됩니다(효과음 재현율 78.7%) — 알람이 *음악*으로 표시될 수 있습니다.
- 원본 파일 112개로 학습했습니다. 말소리가 많이 섞인 징글은 여전히 언어로 읽힐 수 있습니다.

**이 헤드는 언어 프로브와 분리되어 있습니다** — 원파형에서 뽑은 특징(VAD 비율, 2~8Hz 포락선 변조,
스펙트럼 중심·평탄도·플럭스, RMS 변화)에 11개 계수의 로지스틱 회귀만 적용하므로 29개 언어 정확도에는
영향을 주지 않습니다(gold 0.9868 유지).

#### 임베딩 대신 신호 특징을 쓰는 이유

768차원 임베딩을 재사용하면 추가 비용 없이 음악 헤드를 붙일 수 있어 매력적입니다. 실측 결과는 위험합니다:

| gold 발화 + 음악/효과음 112파일로 학습 | gold 홀드아웃 | **실제 유튜브 발화 80창** |
|---|---|---|
| EG2 임베딩 768d 로지스틱 | AUC **1.000**, 검출 100% | **56.6%를 음악으로 오판** |
| 언어 프로브 반응(margin·엔트로피·센트로이드 간격) | AUC 0.983, 검출 97.7% | 9.4% 오판 |
| 신호 특징 + VAD (배포본) | AUC 0.984, 검출 98.8% | **3.8%만 오판** |

임베딩 헤드가 학습 분포에서 완벽한 이유는 그것이 *"스튜디오 녹음 vs 그 외"* 라는 지름길을 배웠기
때문입니다 — "발화 vs 음악"이 아닙니다. 실제 유튜브 오디오(압축·잔향·배경음)에서는 절반 이상을
음악으로 오판합니다. 신호 특징은 대상 자체(VAD 발화 존재, 2~8Hz 음절 변조)를 측정하므로 버팁니다.

**하이브리드(신호 + 프로브 반응) — 측정했지만 채택하지 않음.** 신호 특징 11개에 프로브 반응
6개(최고점수·margin·엔트로피·센트로이드/코사인 간격)를 붙인 17특징 로지스틱은 개선되지만 폭이 작습니다:

| 5-fold out-of-fold · 발화 오탐 0.5% 임계 | AUC | 기악 | 보컬 | 효과음 | 유튜브 오탐 |
|---|---|---|---|---|---|
| 신호만 (11, VAD 포함) | 0.9851 | 97.5% | 80.0% | 95.7% | 4.3% |
| 프로브 반응만 (6) | 0.9767 | 67.9% | 18.3% | 72.3% | 5.0% |
| **하이브리드 (17, C=1)** | **0.9918** | **100%** | 80.0% | 97.9% | **3.6%** |

채택하지 않는 이유는 프로브 반응을 얻으려면 **임베딩이 필요**하기 때문입니다. 그러면 음악 창마다
현재 파형만으로 판정해 아끼던 ~0.4초 임베딩 비용을 다시 치릅니다. AUC 0.7포인트 이득으로는
무음 시 0% CPU로 대기하는 위젯에서 그 비용을 정당화할 수 없습니다.

재현: `data/raw/speech_music/compare_embed_signal.json`, 699초 유튜브 오디오에서 오탐 3.8%,
VAD 비율 중앙 0.93.

### 라이브 데스크톱 위젯

시스템 출력음을 WASAPI 루프백으로 캡처해 5초 링버퍼를 유지하고, 2초마다 다시 판정합니다.

```bash
python app/live_langid.py
```

창을 아무 곳이나 드래그해 이동하고, 우측 상단 **×** 를 누르면 종료됩니다. 우클릭 메뉴에서 일시정지/종료도 가능합니다.

**소리가 없으면 연산하지 않습니다.** 새 오디오가 실제로 들어왔을 때만 임베딩하므로, 무음 상태의
CPU 사용률은 **0%** 입니다(실측). 재생 중에는 **약 1코어**를 씁니다(2초 주기·4코어 기준 실측 99%,
1초 주기에서 210%였던 값). 재생이 멈추면 마지막 판정을 그대로 두고 같은 버퍼를 다시 계산하지 않습니다.

| 환경변수 | 기본값 | 의미 |
|---|---|---|
| `EG2_HOP` | `2.0` | 판정 주기(초) — CPU를 좌우하는 주 손잡이 |
| `EG2_IDLE_HOP` | `4.0` | 무음일 때의 폴링 주기 |
| `EG2_THREADS` | `2` | 임베딩 세션의 ONNX Runtime 스레드 수 |
| `EG2_DEBUG` | — | 틱마다 `rms`·생략 사유를 출력 |
| `EG2_LANG` | OS 로캘 | 위젯 표시 언어: `en` 또는 `ko` |
| `EG2_HOLD` | `20` | 음악 구간으로 바뀌어도 최근 언어를 유지하는 시간(초) |
| `EG2_MODE` | `balanced` | `balanced` · `fast`(3초 창·1.5초 홉) · `precise` |
| `EG2_WINDOW` | `5` | 판정 창(초) — 응답 지연의 하한 |
| `EG2_PREVIEW` | `3` | 무음→발화 전환 시 짧은 창으로 먼저 표시("확인 중"). 0이면 끔 |
| `EG2_VERIFY` | `6` | 음악이 나타난 뒤 첫 재확인 간격(초). 0이면 끔 |
| `EG2_VERIFY_MAX` | `20` | 백오프 상한 — 음악이 계속되면 간격이 2배씩 늘어남 |
| `EG2_VERIFY_MARGIN` | `0.4` | 음악 판정을 뒤집는 데 필요한 프로브 margin |

**재확인의 CPU 비용 — 실측**(실행 중인 위젯, 10초 구간):

| 상태 | 음악 감지 OFF (`EG2_NOMUSIC=1`) | 음악 감지 ON (기본) |
|---|---|---|
| 무음 | 0% | **0%** |
| 발화 | 121~136% | **125~150%** |
| 음악 재생 | **117~142%** | **11~32%** |

각 10초 × 4회, 120초 자산 기준. 두 가지가 드러납니다:

- **음악 감지는 CPU를 쓰는 기능이 아니라 아껴 주는 기능입니다.** 끄면 음악도 언어 판정 대상이 되어
  매 창마다 임베딩을 돌므로, 음악 재생이 발화만큼(≈1.3코어) 비싸집니다. 켜면 음악 창은 파형만으로
  10ms에 판정하고 가끔만 프로브로 재확인합니다.
- **발화에서는 5~10% 더 씁니다** — 특징 추출 + VAD 비용이고, "언제 임베딩하지 않을지"를 알기 위한 값입니다.

어느 쪽이든 가장 비싼 상태는 발화입니다(2초마다 임베딩). `EG2_HOP`을 3~4초로 올리면 절반이 됩니다.

재확인은 임베딩 1회라, 6초마다 돌리면 음악 재생이 발화만큼 비싸집니다. 지금은 음악이 나타나면 즉시
한 번 확인하고, 음악이 이어지면 6 → 12 → 20초로 간격을 늘리며, 발화를 찾는 즉시 6초로 되돌립니다.
디버그 로그로 확인: `[verify] delay=6 → 12 → 20` 후 `→ speech`에서 리셋.
| `EG2_HYBRID` | `0` | `1`이면 프로브 반응까지 사용(느림) |

**최근 언어 유지.** 시끄러운 배경음 위의 인터뷰나, 진행자가 잠깐 말을 멈추는 게임 방송에는 실제로
음악만 있는 5초 창이 섞입니다. 말이 끊겼다고 바로 *음악*으로 바꾸지 않고 `EG2_HOLD` 초 동안
마지막 언어를 흐린 점과 함께 유지합니다(`음악 구간 · 최근 언어 유지`). 그 시간이 지나면 *음악*을 표시합니다.

위젯은 **기본이 영어**이고, Windows 표시 언어가 한국어이면(`GetUserDefaultUILanguage()` = 0x0412)
**한국어로 자동 전환**됩니다. 언어 이름과 상태 문구가 모두 그 선택을 따릅니다.
`EG2_LANG=ko` / `EG2_LANG=en` 으로 강제할 수 있습니다. 화면의 퍼센트는 `p_correct`(정답 확률)입니다.

## 파일 전체 분석

실시간 위젯은 *지금 무슨 언어인가*를 답합니다. 이 기능은 *녹음 파일 어디서 어느 언어가 나오는가* —
구간별 시작·끝 시각과 전체 비중을 냅니다.

```bash
python -m eg2_langid.analyze 인터뷰.mp4 --json timeline.json
```

```
파일: mix_ko_music_en.wav  0:37 (창 5s · 홉 1s)

    0:00–0:14     한국어           99%  (12창)
    0:14–0:23     [음악/효과음]
    0:23–0:34     영어             99%  (11창)
    0:34–0:37     [무음]

비중(발화 구간만): 한국어 56.0% · 영어 44.0%
판정 불가 0:00 (0.0%) · 음악 0:09 (24.3%) · 무음 0:03 (8.1%)
```

실시간과 달리 급하지 않으므로 **홉 1초**로 촘촘히 훑고, 창을 구간으로 병합합니다(3창 중앙값
스무딩 + 짧은 구간 흡수).

**음악 처리는 정책 선택**(`--music`)입니다. 잘못 제외하느니 안 하는 게 나을 수 있기 때문입니다.
정답을 아는 파일(한국어 12초 → 음악 10초 → 영어 12초 → 무음)로 실측한 결과:

| `--music` | 동작 | 그 파일에서의 결과 |
|---|---|---|
| **`mark`** (기본) | 음악 확률이 높아도 **언어 margin이 낮을 때만**(< `--music-margin 0.3`) 음악으로 | ko 0–14 · **[음악] 14–23** · en 23–34 · [무음] 34–37 |
| `off` | 음악 판정을 전혀 하지 않음 | ko **0–15** · en **15–34** — 음악 구간이 언어로 집계됨 |
| `gate` | 음악 확률만 보고 제외 | 큰 음악 위의 발화가 삼켜질 수 있음 |

`mark`가 안전한 이유는 margin입니다: 같은 파일에서 음악만 있는 창은 margin 0.02~0.11, 발화는
0.62~0.85입니다. 즉 **배경음이 깔린 인터뷰는 VAD가 0.2 아래로 떨어져도 발화로 남습니다** — 실시간
위젯에서 음악 판정이 발화를 가로채던 바로 그 실패 모드입니다.

```bash
python -m eg2_langid.analyze FILE --hop 1 --window 5 --min-seg 2 --music mark --json out.json
```

## 실시간 API

위젯은 여러 출력 중 하나일 뿐이고, 같은 엔진을 다른 프로그램이 그대로 씁니다.

```bash
python -m eg2_langid.server                    # http://127.0.0.1:8730
python -m eg2_langid.server --json             # stdout으로 NDJSON도
python app/live_langid.py --json               # 위젯 + NDJSON
python -m eg2_langid.server --no-http --json   # 포트 없이 파이프만
```

| 엔드포인트 | 반환 |
|---|---|
| `GET /health` | `{ok, ready, device, window_sec}` |
| `GET /now` | 최신 판정 1건(JSON) |
| `GET /events` | NDJSON 스트림 — 판정마다 한 줄, keep-alive |
| `POST /detect?window=5` | 본문 = 오디오 파일 바이트(wav/mp3/m4a…) → 판정 1회 |

```json
{"seq":42,"ts":1767225600.12,"status":"speech","lang":"ko_kr","label":"ko_kr",
 "p_correct":0.99,"confidence":0.512,"margin":0.6307,"kind":"speech",
 "window_sec":5.0,"process_ms":969,"preview":false,"silent_run":0,
 "device":"스피커(Realtek(R) Audio) [Loopback]"}
```

`status`는 `starting` · `silent` · `speech` · `unknown` · `music` · `sfx` · `paused` · `error` 중 하나이고,
`preview: true`는 다음 창에서 확정으로 교체될 미리보기입니다. 서버는 기본적으로 `127.0.0.1`에만
바인드하며, 외부 노출은 `--host`(예: Tailscale 주소)로 지정합니다.

## 모델 및 양자화

프로브는 768차원 L2 정규화 오디오 임베딩을 입력으로 받습니다. 임베딩 모델은 패키지에 포함되지
않으며, sentence-embedding 출력을 내보내는 EmbeddingGemma 2 ONNX 빌드라면 무엇이든 붙일 수 있습니다.

**이 문서의 수치를 측정한 구성**

| 항목 | 값 |
|---|---|
| 가중치 형식 | **int8 블록 양자화 — `MatMulNBits` `bits=8`, `accuracy_level=4`** ("q8-al4") |
| 파일 | 오디오 인코더 340MB + 백본 314MB (**654MB**) |
| 상주 메모리 | 약 0.6GB |
| 지연 | 27초 청크당 0.4~1.2초 (CPU 4스레드) |

배포본을 노드 단위로 확인하면 오디오 인코더에 `MatMulNBits`(bits=8) 123개, 백본에 146개가 있습니다 —
즉 **int8 가중치**이며, 업스트림이 배포하는 `*_quantized.onnx` 계열과 같은 구성입니다.

**CPU에서 q8을 쓰는 이유**

| 변형 | 디스크 | CPU 메모리 | 비고 |
|---|---|---|---|
| **q8 (int8 블록)** | 654MB | **양자화 세트 중 최소** | 이 문서의 모든 수치를 낸 구성 |
| q4 (int4 블록) | 363MB | 비슷함 | 업스트림에 존재(`*_q4.onnx`). 디스크만 작고 이 프로젝트에서 미측정 |
| q4f16 | 327MB | **더 큼** | fp16 활성화 유지 — 이 모델 계열 실측 commit ≈559MB (q8은 ≈466MB) |
| fp16 | 1.1GB | 최대 | 품질 기준선 |

CPU에서는 **q8이 균형점**입니다. int8 가중치 + int8 연산(`accuracy_level=4`)이라 파일이 더 커도
활성화가 작게 유지돼 실사용 메모리는 q4f16보다 적습니다. q4가 이기는 건 디스크 크기뿐입니다.

**양자화 가중치를 GPU 실행 프로바이더에 올리지 마세요.** `MatMulNBits` 는 DirectML·CUDA 커널이
없어 해당 노드가 **조용히 CPU로 폴백**됩니다. GPU 메모리는 잡아먹고 속도 이득은 얻지 못합니다.

> 이 문서의 모든 수치는 q8-al4 빌드 기준입니다. 업스트림에는 fp32 / fp16 / q4 / q4f16 빌드도
> 있으므로 파일 교체로 바꿀 수 있고, 어댑터는 양자화 방식과 무관하게 동작합니다.

## 한계

- 라이브 위젯은 **Windows에서만 검증**했습니다 (WASAPI 루프백). 패키지 자체는 플랫폼 독립적입니다.
- Windows 캡처는 장치 레이트(예: 192kHz)로 받아 메모리에서 16kHz로 리샘플링합니다.
- 창이 3초보다 짧아지면 정확도가 급격히 떨어집니다. **5초를 권장**합니다.
- 음악·비발화는 전용 클래스가 아니라 게이트가 "알 수 없음"으로 처리합니다.
- 말레이어/인도네시아어 모호성은 언어 자체의 성질이라 데이터를 늘려도 완전히 해결되지 않습니다.
